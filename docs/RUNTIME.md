# Runtime — hợp đồng Phase 2

Nguồn sự thật kiến trúc: [ARCHITECTURE.md](../ARCHITECTURE.md).

- Runtime production resolve từ Tauri resource directory + verified manifest; không lấy từ PATH/LocalWP/Homebrew.
- Development resolve qua cấu hình developer riêng, đường dẫn tuyệt đối bên `runtime/development/`; không yêu cầu PHP/DB global.
- Manifest theo target: `x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, `x86_64-apple-darwin`. Mỗi artifact pin version/hash/source/license và dependent DLL/dylib.
- Windows x64 development runtime hiện pin PHP 8.4.25 NTS VS17 x64 (`43a8f67ed2e5223fafb21293c85976361808855405278cef2cf3037c3ae2529c`), Caddy 2.11.4 (`1708333f79e274c7697285afe6d592ab39314e0b131e9ec6bea08ad27df62ebf`) và MariaDB 11.4.13 winx64 ZIP (`d62986d433eeebfde218560b276103831604a61e929e87f1a17f5aebd80257e2`). Template manifest và `php.ini` nằm trong `scripts/runtime-development/`; `scripts/stage-runtime-development.ps1` xác minh hash trước extract vào `runtime/development/x86_64-pc-windows-msvc/` (ignored).
- PHP development `php.ini` bật mysqli, PDO MySQL, curl, openssl, mbstring, intl, zip, gd, fileinfo và Zend OPcache từ bundle đã pin. DOM/XML được kiểm bằng module list vì các module tương ứng là phần của build PHP. Không kế thừa cấu hình PHP máy người dùng.
- MariaDB dùng `mariadbd.exe`, `mariadb.exe` và `mariadb-install-db.exe` từ bundle đã pin; runtime manager phải truyền explicit defaults-file, basedir/datadir/port/bind-address. Không đọc my.ini/my.cnf global và Phase 2 startup không tự initialize datadir chưa provision.
- MariaDB readiness là authenticated SQL probe; PHP readiness là response nhận diện đúng instance; application health do plugin xác nhận.
- PHP document root là `site/`; router script thuộc desktop layer phải xử lý permalink, static files, path traversal và chặn file nhạy cảm, không sửa WP core.
- Trước provisioning, Phase 2 dùng fixture riêng `fixture/router.php` cho HTTP readiness tại `/__coffeepos_runtime_health`. Fixture này chỉ chứng minh đúng PHP process đã sẵn sàng; không thay application health của WordPress/plugin.
- Mỗi start attempt có timeout, stderr redaction, cleanup toàn bộ child đã tạo. Shutdown/crash/parent-kill phải test riêng trên từng OS.
- Log tách application/runtime/php/database/wordpress, có size bounds và export redacted.
- Windows runtime manager hiện dùng Job Object `KILL_ON_JOB_CLOSE`, `CREATE_NO_WINDOW`, dynamic loopback ports và authenticated SQL probe. PHP readiness dùng file nonce riêng cho từng start attempt; `fs::canonicalize` chỉ phục vụ kiểm tra containment, còn đường dẫn truyền sang Windows PHP/MariaDB được chuyển về dạng command-compatible thay vì `\\?\...`.
- Phase 5.6 ban đầu dùng PHP router wrapper + marker để admission/drain trên single-process `php -S`. Phase 6.2 thay serving stack: Caddy graceful `/stop` với bounded `grace_period` là drain fence chính cho request đang chạy; sau khi Caddy dừng Desktop mới terminate PHP FastCGI master rồi shutdown MariaDB. `config/runtime-draining.flag` vẫn là fallback admission gate nếu graceful Caddy stop không hoàn tất và được clear trước clean startup.
- PHP HTTP process readiness giữ timeout 10 giây. Từ Phase 4.8, WordPress application readiness có timeout riêng 45 giây vì real WooCommerce-active baseline có thể cần hơn 10 giây cho dynamic request đầu tiên sau activation/start; E2E xác nhận đây là Woo/WordPress startup behavior và vẫn xảy ra khi inactive CoffeePOS directory được tạm loại khỏi site. Timeout tách riêng để không làm chậm phát hiện PHP process startup failure.
- Smoke test 2026-09-17 với datadir disposable đã PASS chuỗi `start → stop → restart-from-stopped → restart-while-running → stop`, dùng đúng PHP/MariaDB staged; sau test không còn process staged chạy nền.

Gate development trước provisioning là chạy bằng artifact đã pin với executable/config tường minh, không lấy PHP/MariaDB từ PATH hoặc LocalWP; Phase 2–3 đã có bằng chứng Windows cho phạm vi này. Kiểm chứng trên máy sạch không dev tools thuộc Phase 9.3, chưa được coi là đã pass. Trên macOS kiểm tra `otool -L`, rpath và dependencies để loại đường dẫn `/opt/homebrew` hoặc build-machine paths.

Phase 4.2 phân biệt runtime readiness với WordPress health sau mỗi start/restart. Từ Phase 4.10, `provisioning.ready` chứng minh installation + activation + machine-credential bootstrap, còn live CoffeePOS state đến từ authenticated `/wp-json/coffeepos/v1/system/status` sau khi WordPress healthy. Runtime xóa CoffeePOS health cũ khi stop/failure/process death và reprobe định kỳ khi đang chạy; missing credential, auth reject, contract/schema lỗi và transport/bootstrap lỗi được giữ tách khỏi plugin-reported degraded dependency state. Tải POS thật vẫn thuộc Phase 5.4 trước gate LAN/release trong [ROADMAP.md](ROADMAP.md).

Phase 6.1 thêm snapshot diagnostics riêng nhưng tái sử dụng các probe trên: MariaDB chạy authenticated `SELECT 1`, PHP chạy nonce probe tạm, WordPress chạy readiness HTTP, rồi CoffeePOS machine-health phân loại application dependencies. Snapshot được giữ dưới lifecycle lock để không chạy song song với start/stop/restart/shutdown; probe PHP tạm chỉ được ghi nhận sau khi write+flush thành công, còn lỗi sau create phải đóng và cleanup file trước khi trả về. Payload machine-health hợp lệ mới được dùng để gán lỗi WooCommerce/CoffeePOS; failure không có payload giữ dependency ở trạng thái chưa xác minh.

Phase 6.2 đã triển khai performance architecture Windows-first: `get_runtime_info` là fast process/status + cached-health snapshot; cron và application-health nằm ở maintenance path riêng được serialize bằng lifecycle lock. Tauri lifecycle/diagnostics/exit blocking work chạy qua blocking worker. Caddy serve static/uploads và proxy PHP tới một private FastCGI port; một `php-cgi` master dùng 4 worker (`PHP_FCGI_CHILDREN=4`, max 500 request/worker), tất cả giữ loopback/dynamic ports và Job Object containment. Readiness nonce đi qua Caddy → FastCGI và xác minh OPcache active trên web SAPI. Disposable lifecycle/concurrency smoke pass và không để orphan; xem số benchmark/acceptance ở [PHASE-06.2.md](PHASE-06.2.md).

Phase 8 giữ nguyên boundary private của MariaDB, PHP FastCGI, Caddy admin và native machine-health. LAN mode chỉ thêm một explicit web listener trên adapter IPv4 được user approve; canonical LAN origin dùng HTTPS với TLS identity thuộc target profile, trong khi internal readiness/management tiếp tục đi qua loopback. Network apply là lifecycle transaction có health verification + rollback local-only, không phải raw bind_host edit. Network mode, adapter identity và TLS private material không đi theo portable backup. Xem [PHASE-08.1.md](PHASE-08.1.md), [PHASE-08.2.md](PHASE-08.2.md) và [PHASE-08.3.md](PHASE-08.3.md).
